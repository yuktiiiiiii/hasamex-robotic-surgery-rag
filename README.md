# European Robotic Surgery Transcript Analyzer

An evidence-first AI application for analyzing expert interview transcripts from the European robotic surgery market.

The application processes expert interview transcripts, answers the predefined interview-guide questions, extracts exact supporting quotes with timestamps, identifies common themes and documented differences, and allows users to ask questions across all loaded transcripts.

---

## Project Objective

The goal of this project is to analyze expert-call transcripts for a European robotic surgery market study.

The application is designed around one principle:

> Every important answer should be traceable back to the original transcript.

The system therefore preserves:

- Expert name
- Role
- Market
- Speaker
- Timestamp
- Exact transcript text
- Source filename

---

## Key Features

### 1. Transcript Upload

Upload exactly three `.txt` expert transcripts.

The application automatically:

- Parses transcript headers
- Identifies speakers
- Preserves timestamps
- Extracts expert responses
- Builds a searchable retrieval index

The provided sample transcripts cover:

- France — Dr. Jean Martin
- Germany — Anna Keller
- United Kingdom — Dr. Emily Carter

---

### 2. Interview Guide Analysis

The application supports the six predefined project questions:

1. How would you describe current adoption of robotic surgery in your market?
2. What are the main barriers to adoption?
3. How important are hospital budgets and ROI in purchasing decisions?
4. How important are surgeon training and clinical outcomes?
5. What adoption trend do you expect over the next 3–5 years?
6. What is the typical hospital decision-making timeline for purchasing a new robotic system?

The application produces answers separately for each expert/market.

The fourth guide question combines the transcript's separate training and clinical-outcomes responses.

---

### 3. Exact Quotes and Timestamps

Each answer is linked to the original transcript evidence.

For example:

```text
France — Dr. Jean Martin — 01:20

"The biggest issue is still capital budget approval..."
````

The quote is taken directly from the stored transcript data rather than being generated by the language model.

---

### 4. Common Themes

The application identifies themes appearing across multiple expert transcripts, including areas such as:

* Cost / budget / economics
* Training / workforce
* Procedure volume / utilisation
* Clinical outcomes
* Uneven hospital access / adoption
* Gradual growth

Each detected theme is accompanied by supporting transcript evidence.

---

### 5. Documented Differences

The application highlights differences in expert emphasis, including:

* Role of economics in purchasing
* Expected adoption growth
* Purchase decision timelines

The system reports what the experts said without assigning a winner or ranking the markets.

---

### 6. Ask AI

Users can ask free-form questions across all loaded transcripts.

Example:

```text
What do the experts say about surgeon training?
```

The system:

1. Retrieves relevant transcript evidence.
2. Passes the evidence to the answer generator.
3. Generates a grounded response.
4. Displays supporting transcript sources.
5. Preserves the original quote and timestamp.

## Retrieval Pipeline

The application uses hybrid retrieval.

### Dense Retrieval

`sentence-transformers/all-MiniLM-L6-v2`

is used to convert transcript chunks and queries into embeddings.

FAISS is then used for semantic similarity search.

### Keyword Retrieval

BM25 is used to capture important exact keyword matches.

### Hybrid Retrieval

Dense and BM25 rankings are combined using Reciprocal Rank Fusion (RRF).

This provides both:

* semantic matching
* keyword matching

---

## Relevance / Hallucination Control

A major requirement of the assignment is:

> Do not invent information.

The application therefore uses several safeguards.

### Expert-only Retrieval

Interviewer questions are excluded from the expert-response chunk index.

This prevents the retriever from treating a question such as:

```text
What are the main barriers?
```

as an expert answer.

---

### Relevance Gate

Retrieved evidence must pass a minimum semantic similarity threshold before being sent to the answer generator.

If no sufficiently relevant evidence is found, the application abstains instead of generating an unsupported answer.

Example:

```text
The transcripts do not provide enough information to answer this.
```

---

### Source-grounded Generation

For free-form questions, the language model receives only retrieved transcript evidence.

The generation prompt explicitly instructs the model to:

* use only supplied evidence
* avoid outside knowledge
* avoid inventing facts
* avoid inventing quotes
* preserve the meaning of the source

---

### Source Quotes Are Not LLM-generated

Exact quotes are taken directly from the stored transcript records.

This separates:

```text
Generated answer
```

from:

```text
Original source evidence
```

and makes source verification easier.

---

## Question-Aware Transcript Mapping

The supplied transcripts contain seven expert responses per interview.

The application maps them to the six project questions:

```text
Transcript Q&A 0 -> Q1 Current adoption
Transcript Q&A 1 -> Q2 Barriers
Transcript Q&A 2 -> Q3 Budget / ROI
Transcript Q&A 3 -> Q4 Training
Transcript Q&A 4 -> Q4 Clinical outcomes
Transcript Q&A 5 -> Q5 Adoption trend
Transcript Q&A 6 -> Q6 Purchase timeline
```

This is used for the fixed interview-guide analysis.

## Scaling from 3 to 30+ Transcripts

The current architecture separates parsing, retrieval, generation and UI.

Therefore the same pipeline can scale from three transcripts to a much larger collection.

For a larger deployment, I would add:

### Persistent Vector Storage

Instead of rebuilding FAISS on every run, embeddings can be stored persistently in a vector database.

Examples:

* Qdrant
* FAISS on disk
* another managed vector store

### Metadata Filtering

Each document/chunk can carry metadata such as:

```text
project_id
expert_id
expert_name
role
market
timestamp
source_file
```

This allows filtering before retrieval.

### Batch Processing

Thirty or more transcripts can be parsed and embedded in batches rather than processing them interactively.

### Caching

Embeddings and loaded models can be cached so that repeated application runs do not recompute the same data.

### Background Processing

For larger uploads, transcript parsing and indexing can be moved to background workers while the UI reports processing progress.

## Design Decisions

### Why hybrid retrieval?

Dense retrieval helps with semantic similarity.

BM25 helps when the user uses the same terminology as the transcript.

Combining both makes retrieval more robust than relying on only one method.

### Why preserve metadata in every chunk?

Because source traceability is a core requirement.

Keeping the timestamp, expert, market and source file with every chunk means the application can return evidence without reconstructing the source later.

### Why not let the LLM generate quotes?

Generated quotes can contain wording that is not present in the original document.

The application therefore returns the original transcript statement directly as the quote.

---

## Limitations

This project is designed as a local technical-case prototype.

Current limitations include:

* The local FLAN-T5 model is lightweight and may produce weaker summaries than larger hosted LLMs.
* Transcript parsing assumes the provided timestamp/speaker format.
* The relevance threshold requires tuning against a larger evaluation set.
* Theme detection currently uses rule-based keyword matching.
* The current indexing pipeline is rebuilt when transcripts are loaded.

These can be improved for a production implementation.

## Project Principle

The central design principle is:

```text
Retrieve evidence first.
Generate only from retrieved evidence.
Show the original source.
```

This keeps the application focused on reliable, traceable transcript analysis rather than unsupported generation.
